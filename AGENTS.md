## Repo layout
This repo collects multiple agent-based model builders, one per directory. See README.md.

- `prompt-agent/` — a Foundry prompt agent ("ml-trainer") with the Code Interpreter tool that trains a scikit-learn model (regression / classification / clustering) from an uploaded dataset and returns model.pkl. See prompt-agent/README.md.
- `copilot-agent/` — a **GitHub Copilot agent hosted on Foundry** (Agent Framework `GitHubCopilotAgent` + `ResponsesHostServer`, Responses protocol). The Copilot CLI harness runs INSIDE the hosted container's per-session micro-VM to train by writing/running code. Not restricted to scikit-learn; logs the model with MLflow so the export carries its own environment alongside model.pkl. Inference routes to the Foundry deployment via BYOK + Entra OAuth. Deploy with `azd` from the `copilot-agent/` root. See copilot-agent/README.md.
- `copilot-toolbox-agent/` — a **GitHub Copilot agent hosted on Foundry that executes code via a Foundry Toolbox Code Interpreter** (`src/copilot-toolbox-trainer/main.py`). Same `GitHubCopilotAgent` + BYOK inference as `copilot-agent/`, but the harness is given the toolbox MCP endpoint via `GitHubCopilotOptions(mcp_servers=...)`, and `COPILOT_ALLOWED_PERMISSIONS` defaults to `mcp,read` (no local `shell`) so ALL code runs in the toolbox's managed sandbox, not the container. Lightweight image (no local ML stack). Deploy with `azd` from the `copilot-toolbox-agent/` root. See copilot-toolbox-agent/README.md.

## Notes
- The Code Interpreter sandbox uses Python 3.11 + scikit-learn 1.1.3; downloaded .pkl models must be loaded with a matching sklearn version (see prompt-agent/requirements-loader.txt).
- The Responses API uses `agent_reference` (not the deprecated `agent`) in extra_body to target the agent.
- copilot-agent is a hosted Foundry agent built on the `agent-framework-agent-basic-responses` pattern: `src/copilot-ml-trainer/main.py` (GitHubCopilotAgent + BYOK ProviderConfig + ResponsesHostServer), Dockerfile (python:3.12-slim + Node 22 + `@github/copilot` CLI + the ML stack + `libgomp1` for xgboost/lightgbm), and `uv.toml` + Dockerfile both override `github-copilot-sdk==1.0.11` (1.0.2 lacks `bearer_token_provider` and silently 401s BYOK). `FOUNDRY_*`/`AGENT_*` env names are reserved, so it uses `BYOK_*`. Each session gets its own micro-VM, so file build-up / cross-user clobbering is a non-issue.
- copilot-toolbox-agent reuses the copilot-agent pattern but wires a Foundry **Toolbox** (`code-exec`, exposing a `code_interpreter` tool) into the harness as an HTTP MCP server. The harness only supports a STATIC `Authorization` header on an MCP server, so the toolbox bearer token is minted once at startup (≈1h lifetime; a long-lived container may need a restart to re-mint). Uses `BYOK_*` + `TOOLBOX_*` env names. The per-agent instance identity needs *Azure AI User* on the project (to call the toolbox) in addition to the model role.
- Hosted-agent `azd` deploy of an EXISTING Foundry project requires `FOUNDRY_PROJECT_ENDPOINT` (and `FOUNDRY_MODEL_ENDPOINT`/`FOUNDRY_TOKEN_SCOPE`) in the azd env plus a `AZURE_CONTAINER_REGISTRY_ENDPOINT`/`_RESOURCE_ID`; run `azd provision` before `azd deploy`. `azd provision` can blank the ACR endpoint (ACR mode `none`), so re-set it before deploying.
